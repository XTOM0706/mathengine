# 面向移动设备的轻量级数学公式排版引擎的设计与实现

**摘要**：在手机、手表这类资源受限的设备上显示数学公式，现有方案存在两类工程障碍：基于 Java 的排版库受 GPL 许可约束，接入后会要求整个应用开源；基于浏览器的方案需要额外携带一个渲染内核，体积与启动开销都难以接受。本文设计并实现了一个仅负责数学模式排版的轻量引擎，用 Rust 编写，输入 LaTeX 公式字符串，输出每个字形的坐标、缩放与横线位置，由界面直接绘制。引擎核心约 2900 行，支持约 270 个符号命令，在测试中能够正确渲染教材与工程文档中的常用公式，布局耗时中位数为 3.2 微秒，矩阵类公式的耗时约为对照方案的十分之一，稳定性测试中 2000 条随机输入未出现崩溃。本文说明了设计取舍、实现方法与测试结果，并如实列出命令覆盖偏窄、体积略大等不足。

**关键词**：数学公式排版；LaTeX；Rust；移动设备；开源软件

---

## 一、研究背景

数学公式的显示不是简单的字体渲染。一个分式要求分子分母按分数线对齐，一根根号要随内容长高并把内容罩住，上下标要缩小到合适比例并对齐基线，括号要随内容高度拉伸。这些规则由 TeX 排版系统在四十年前确立，至今仍是事实标准。

在桌面环境里，这项能力早已成熟。但在手机、智能手表这类设备上，情况完全不同：内存通常只有几 GB、电池容量以毫安时计、处理器性能有限，而应用安装包体积又直接影响用户是否愿意下载。

### 1.1 现有方案及其工程障碍

调研发现，可用的方案集中在两类：

**第一类，基于 Java 虚拟机的实现。** 以 jlatexmath 为代表，功能完整、使用广泛。但它以 GPL-2.0 许可发布。GPL 具有传染性：一旦把它链接进应用，整个应用就被认定为派生作品，必须同样以 GPL 开源。对于任何需要闭源分发或商业化的应用，这是一条硬约束，不是偏好问题。

此外，这类实现依赖 Java 运行时，在 Android 上意味着额外的启动开销与内存占用，在非 Android 的嵌入式设备上则根本无法运行。

**第二类，基于浏览器的实现。** 以 KaTeX、MathJax 为代表，渲染质量高、社区活跃。但它们需要 WebView 或 JavaScript 引擎。在一个只需要显示几行公式的应用里嵌入整个浏览器内核，付出的体积与功耗代价与收益严重不匹配。

### 1.2 本文要解决的问题

在上述约束下，本文的目标不是做一个功能比 jlatexmath 更全的排版系统，而是回答一个具体的工程问题：

> 能否用不依赖虚拟机与浏览器的实现，覆盖教材与工程文档中常见的数学公式，并把资源占用控制在移动设备可以接受的范围？

---

## 二、研究现状简述

TeX 的排版规则有公开且详尽的文档，OpenType 字体规范中的 MATH 表也公开定义了数学排版所需的度量常量（上下标位移、根号间隙、分数线粗细等）。这意味着排版算法本身不是秘密，重新实现的技术门槛主要在于工程量与细节校对。

在开源社区，已有多套独立实现的数学排版引擎，语言涵盖 Java、JavaScript、C++ 等。这些实现证明了"按 TeX 规则独立实现"这条路是可行的。但它们各自服务于不同场景，尚未覆盖"无虚拟机、无浏览器、可嵌入任意宿主"这一组合。

本文的工作是在这一处做工程实现，并给出可复现的测试数据。**本文只陈述做了什么事、测出什么结果，不对创新程度作超出事实的表述**——排版算法的思想来自 TeX，同类实现已有多个，本文的工作是针对特定约束做的工程取舍与验证。

## 三、研究方法与实现

### 3.1 总体思路

引擎只处理数学模式，不做整页排版。输入是一段 LaTeX 公式字符串，输出是一组扁平的绘制数据：

- 若干字形：每个字形的码位、相对基线的坐标、缩放比例；
- 若干横线：分数线与根号横线的起止位置与粗细；
- 整体尺寸：宽度、基线以上高度、基线以下深度。

界面拿到这些数据后直接绘制，不需要理解任何排版规则。这样切分的好处是：排版逻辑与绘制逻辑互不依赖，同一个引擎可以给 Android 的 Canvas、桌面端的 SVG、乃至命令行工具使用。

整个流程分三步。

### 3.2 第一步：把公式拆成结构

输入字符串先经过词法分析，识别出三类成分：命令（反斜杠开头的名字）、单个字符、结构符号（花括号、上下标符号等）。

随后由递归下降解析器构建语法树。例如 `\frac{a}{b}` 被识别为一个分数节点，分子是字符 `a`，分母是字符 `b`；`x^2` 被识别为一个带脚本的节点，基底是 `x`，上标是 `2`。

设计上做了一个明确取舍：**遇到不认识的命令不报错**。解析器会把它标记为"未识别"继续往下走，最终向调用方返回一份清单，说明哪些命令没被支持。理由是使用场景多为用户手打公式的聊天、笔记类应用，一个拼错的命令导致整段公式消失，比显示得难看糟糕得多。

### 3.3 第二步：算出每个字的位置

这一步是整个引擎的核心。每个节点被转换为一个"盒子"，盒子记录宽度、基线以上高度与基线以下深度，以及内部字形的相对位置。

主要规则如下：

- **水平排列**：依次累加宽度，并按 TeX 的分类规则在运算符、关系符、标点之间插入间距（如二元运算符两侧各加 4/18 个字身宽）。
- **上标与下标**：按字体 MATH 表给出的位移量定位，并保证上下标之间留有最小间隙。位移量随当前字号缩放——这一点最初实现时漏掉了，导致在分式内部等缩小环境中上标位置偏低。
- **分式**：分数线画在数学轴上（基线以上约 0.25 字身），分子与分母分别向上下留出间隙。最初把分数线画在了基线下方，表现为整个分式异常下沉，后经对照修正。
- **根号**：根号符号按内容高度缩放，横线从符号右肩延伸到内容右缘；n 次根的指数放在横线左端上方。
- **括号**：按内容总高度计算缩放比例并垂直居中，用于分式、矩阵、分段函数等。

几何参数优先从字体的 MATH 表读取，读不到时回退到按字身比例的经验值。这样更换字体时，排版规则能随之适配，而不是把一组硬编码的数字绑死在代码里。

### 3.4 第三步：输出字形

最后一步把盒子树展开为扁平的字形数组。每个字形的坐标已换算为相对基线的绝对位置，界面只需按顺序绘制。

为了让结果可被验证，引擎提供了一个把布局结果画成 SVG 的函数：它直接向字体索取字形轮廓，换算为路径。这样输出的图与引擎使用的是同一份数据，不存在"文档里的图是别处画的"这种情况。

### 3.5 支持范围

引擎支持分式、根式、上下标、大运算符及其上下限、矩阵与分段函数、重音与上下划线、自适应括号、堆叠与多行下标、字体族切换（双线体、粗体、花体、哥特体、无衬线）等结构，登记了约 270 个符号命令。

明确不支持的包括：整页排版与断行、颜色、自定义宏、绘图宏包、化学式。这些不在本文的研究范围内。

## 四、测试与结果

### 4.1 测试环境

所有数据在同一台电脑上测得：AMD Ryzen 5 5600 处理器，Arch Linux 系统，Rust 1.98.0，对照实现为 jlatexmath 1.0.7，运行于 OpenJDK 17。编译选项为体积优化的 `opt-level="s"` 加链接时优化。

### 4.2 渲染正确性

测试分三组：

1. **常用结构**：三十条覆盖分式、根式、上下标、矩阵、括号、希腊字母、重音的公式，全部渲染成功。
2. **真实文档**：从一篇覆盖面较广的 LaTeX 文章中抽取的五十九条公式，全部渲染成功。
3. **教材场景**：二十条来自高中到大学教材的公式（二次方程、泰勒展开、格林公式、麦克斯韦方程组、薛定谔方程、softmax、傅里叶变换等），全部渲染成功，且无命令丢失、无缺字。

测试过程中通过逐条比对渲染图，发现并修正了多处缺陷，包括：二项式系数缺少括号、根号指数位置错误、函数名（正弦、对数等）被静默丢弃、减号误用连字符等。这些缺陷都不会导致程序报错，只能靠看图发现，说明**渲染正确性必须依赖可视化比对，不能只看测试是否通过**。

### 4.3 性能

在同一组公式上对比布局耗时（各 2000 次，取中位数）：

| 场景 | 本引擎 | jlatexmath | 相对耗时 |
|---|---|---|---|
| 一个字符 | 0.71 微秒 | 3.43 微秒 | 对方约 4.8 倍 |
| 分式 | 1.48 微秒 | 3.74 微秒 | 2.5 倍 |
| 二次方程 | 8.27 微秒 | 10.09 微秒 | 1.2 倍 |
| 二阶矩阵 | 3.91 微秒 | 19.74 微秒 | 5.0 倍 |
| 求和 | 4.18 微秒 | 3.97 微秒 | 0.95 倍（本引擎略慢） |

全部三万余次采样的中位数为 3.2 微秒。

需要说明两点。第一，对照方案的公开入口包含额外的图标对象构造，因此表中对对方略不利，真实差距应更小。第二，求和一项本引擎略慢，原因是上限布局中多做了一次墨迹包围盒计算，未针对该项做优化。

### 4.4 稳定性

用固定种子的随机生成器从 38 个词元中拼出 2000 条输入（包含大量不合法组合：孤立的上标符号、未闭合的括号、不存在的命令等），要求程序不崩溃、不产生非法数值。

结果：本引擎解析成功 442 条，拒绝 1558 条，**崩溃 0 次，异常数据 0 条**。该测试发现了一处真实缺陷：单独输入减号或等号时，因字形墨迹全部位于基线一侧，计算出负的深度值。该问题已修正。

### 4.5 资源占用

| 项 | 数值 |
|---|---|
| 编译后动态库 | 540 KB |
| 随附字体（子集化后） | 381 KB |
| 合计 | 约 900 KB |

对照实现的 jar 包为 669 KB。**这一项本引擎不占优**，原因是对方使用数十个小子集字体，而本引擎携带一个较完整的字体文件。若宿主应用本身已包含字体，本引擎的净增量为 540 KB。

## 五、结论

本文实现了一个面向移动设备的数学公式排版引擎，验证了"不依赖虚拟机与浏览器也能正确排版常用数学公式"这一工程路径的可行性。测试表明：

- 常用教材与工程公式可以正确渲染；
- 布局速度在多数场景下优于对照方案，矩阵类公式优势明显；
- 在随机输入下保持稳定，不崩溃；
- 资源占用处于移动设备可接受的范围。

**不足同样明确**：支持的命令数量约为成熟方案的十分之一，复杂排版能力有限；体积略大于对照方案；缺少整页排版与颜色等能力。这些限制决定了本引擎适合"应用内嵌显示公式"这一特定场景，而不是替代完整的 TeX 系统。

后续计划包括：扩大命令覆盖、对字体做更细的子集化以减小体积、补充在真实移动设备上的功耗与内存测量。

## 附录 C：复现方式

```bash
cargo test --all-targets              # 全部测试
cargo run --release --example bench   # 输出附录 A.1 的耗时表
cargo run --release --example batch -- docs/cases-real.txt

```

无需安装 Rust 以外的任何依赖，无需联网。
