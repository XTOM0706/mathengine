## 二、逐项评估

### 1. Arix —— 最该拿去参赛的那个

**是什么**：给手表做的 AI 助理。语音是第一入口，不做麦克风常开，用抬腕门控 + 分级唤醒控制功耗；对话走云端流式，支持 OpenAI 兼容 / Anthropic / Gemini 三种协议；76 个工具入口、长期记忆、三档权限、加密备份、自动更新；另有 Linux 终端端与 Rust 原生库。

**归属已澄清**（2026-11-13）：

- 参赛主体是 `/media/xtom0706/OTHER/OnyxAI`，**AGPL-3.0**，`git rev-list --count` = **859**，tag 到 **v0.6.7**，与申报简介里的「859 次提交、十一个版本」完全对上。

### 2. K60 跑 iOS —— 技术含量最高，但要摆正定位

**是什么**：在 Redmi K60（SM8475 / mondrian）上把 XNU 内核与 iOS 用户态跑起来。已做到内核侧可引导、GPU 走 Adreno + Turnip + Metal 翻译层出画面（参考样本 pandora 在小米 17 Pro 上到 iOS 16.7 主屏、约 110fps），相机子系统全线 `not implemented`，当前卡在 USB gadget 与配对桩。仓库 `~/hackios`，含 `REPO-SURVEY.md`、`C17-PATHS-WORKLIST.md` 等精确到路径的工程文档。

**为什么值钱**：这项工作的难点是真难点——设备树、内核 KMD、图形翻译层、子系统缺口评估。评审里懂行的人会认得出来。文档做到「精确到文件路径 + 提交号」，这是很多学生项目没有的严谨度。

**必须摆正的定位**：

- 不要说「我让 K60 用上了 iOS」。要说「我完成了在非苹果 SoC 上引导 XNU 的可行性评估与阶段性移植，明确了剩余三个阻塞点」。**未达成的部分主动写出来，比被问出来强得多。**
- 版权与分发红线：苹果代码不可分发。参赛材料只放自研部分（设备树、脚本、逆向分析、移植层），不放任何苹果二进制。
- 实用性会被质疑。提前准备一句回答：「这不是为了让谁用 iOS，是为了验证一颗非苹果 SoC 上内核与图形栈的边界在哪，结论对其他移植工作可复用」。

**申报角度建议**：归到「计算机系统 / 底层软件」方向。研究性项目，重方法轻成果。

## 四、Arix 拆分申报方案

### 拆分的第一原则

拆出来的每一份，必须是「**一个能独立讲完的问题 + 自己的一套验证方法**」。按功能列表切不叫拆分，叫把一个作品剪成四段，评审一眼能看出是同一套东西，反而扣分。

### 可行的四份

| 编号 | 作品名 | 独立要回答的问题 | 主投赛事 | 还缺什么证据 |
|---|---|---|---|---|
| A1 | Arix：手表优先的语音 AI 助理 | 手表这种小屏小电池设备上，AI 助手该怎么设计才真的能用 | 科创赛、宋庆龄奖 | 真机截图、功耗对照、演示视频、版本与许可口径 |
| A2 | **自研 Rust LaTeX 数学排版引擎（mathengine）** | 现有方案 jlatexmath 受 GPL-2.0 约束、依赖 JVM、体积大，能否用纯 Rust 重写一套可嵌入的 TeX 排版实现 | 明天小小科学家、丘奖计算机 | 与 jlatexmath 的横向对照：命令覆盖、布局耗时、.so 体积、内存、渲染一致性的像素比对 |
| A3 | 工具数量与上下文预算的权衡 | 工具越加越多，模型越容易选错，能否在不减能力的前提下把每轮开销压下去 | 丘奖计算机、信息素养活动 | 34 与 76 工具两种配置的选错率对照、每轮 token 实测、失败回写前后对比 |
| A4 | Rust 端侧库与 dna-rs 镜像工具 | 端侧原生计算与系统镜像打包的正确性怎么保证 | 信息素养活动、电子信息类赛事 | cargo 基准数据、25 项缺陷的复现用例与修复前后比对 |

### 四条红线

1. **同一届同一赛事，一个学生通常只能报一个项目。** A1 和 A2 不能同年报科创赛，拆了也递不进去。具体条款每年会改，务必自己核当年章程。
2. **跨赛事可以，但要各报各的口径。** 材料里应互相致谢、写明同源关系，不能装作两个无关作品。同一核心成果反复拿奖，评委一旦发现很被动。
3. **最稳的排法是分年，不是分功能。** 今年 A1 打科创赛把作品立住，明年 A2 或 A3 打研究类赛事。这比一年内把四份全投出去稳得多，而且 A2 的实验数据正好可以在今年做 A1 的时候顺手攒。
4. **拆出去的那份必须能独立运行或独立复现。** A2 不能只给一段代码，要能给出可复现的实验脚本和原始数据；A3 不能只给截图，要给出完整的对照表格。

### 建议的优先级

先做 **A2（mathengine）**，这是现在最该报的那个。

理由：

- **它完全是自己写的**，不存在「上游项目 / 适配层」的原创性质疑，这一点比唤醒链路干净得多。
- **有明确的替代对象和替换理由**：jlatexmath 是 GPL-2.0，放进 Android 应用会有许可传染问题；换成纯 Rust、无 JVM 依赖的实现，动机是工程上真实成立的，不是硬凑。
- **可量化的对比维度齐全**：4109 行 Rust、46 个单元测试、支持的命令范围、`.so` 体积、布局耗时、内存占用，每项都能拿出数字，也能现场跑。
- **答辩好讲**：从 tokenizer → AST → TeX Box 布局 → GlyphRun → Canvas 这条链路，讲清楚「基线对齐、上下标缩放 0.7/0.5、分数线、根号、矩阵」这些具体难点，评审能听懂你确实做了东西。

**唤醒那条不要再提。** 你自己说实现经不起看源码，那就别写进任何材料。凡是评审可能去读源码的部分，材料里写的都必须经得起翻，这是唯一不能赌的地方。A1 作为产品作品材料已写好，按收尾处理，不再追加投入。

### A2 的实验设计（照着做就能出材料）

1. **命令覆盖**：列出 jlatexmath 支持且 Arix 也支持的命令集，给出各自支持数、不支持清单。不要写「全面支持」，写具体的。
2. **布局耗时**：同一批公式（简单分式、嵌套上下标、矩阵、积分、根式各若干）在两个引擎上各跑 N 次，报中位数与 p95。设备与参数写清楚。
3. **产物体积**：`.so` 大小 vs jlatexmath 的 jar 大小，以及两者接入后 APK 的增量。
4. **渲染一致性**：同公式两引擎渲染成图，做像素比对，列出不一致的用例并分析原因。**不一致的地方不必藏，说明为什么**，这比声称 100% 一致可信。
5. **健壮性**：未支持命令的宽容降级行为、超长公式、非法输入的崩溃率。

#### 候选一：RFB(VNC) 协议客户端 —— 已否决

> 代码确凿存在：`terminal/src/main/kotlin/com/arix/terminal/gfx/rfb/RfbClient.kt`（41 KB，1012 行，9 月 27 日最后修改）与 `Keysyms.kt`。`grep` 可查到 `Cipher("DES/ECB/NoPadding")`、`Inflater()`、`ENC_ZRLE = 16`。它是给容器里 `Xvnc` 用的内置查看器。
>
> **但按作者判断，不报。** 理由：真机零验证，仓库里没有一条「画面出来了」的记录，报上去就是把一个没跑通的东西交给评审去发现。此节仅作技术记录，不进任何材料。

协议层 1122 行里 `grep 'import android'` 零命中，只依赖 `Socket`、`BufferedInputStream`、`java.util.zip.Inflater`、`javax.crypto.Cipher("DES/ECB/NoPadding")`，输出是一个 ARGB_8888 的 `IntArray`。

**动机链条完整**：能用的 Android VNC 客户端（AVNC、bVNC、TightVNC Java viewer、LibVNCClient）全是 GPL，链进 APK 整包变 GPL 派生；noVNC 虽是 MPL，但要在容器里再装 websockify，等于多一个安装步骤和一个常驻进程。于是手写。这条理由和 mathengine 换掉 jlatexmath 是同一个逻辑——**许可污染 + 依赖过重**，两个项目串起来讲，能形成一个很硬的技术主张。

**真难点（答辩可直接指行）**：

- RFB 3.7 在 `SecurityTypes=None` 时服务端**不发** `SecurityResult`，多读 4 字节整条流就错位。
- VNC 认证的 DES 密钥每字节要做 **8 bit 位序反转**，且必须用 `SecretKeySpec` 而不是会拒弱密钥的 `DESKeySpec`。
- ZRLE 有五种 subencoding（raw / 纯色 / 调色板位打包 / 纯 RLE / 调色板 RLE），调色板要**按行补齐到字节边界**，不补从第二行起就是斜条纹；32bpp 下 CPIXEL 只有 3 字节。
- 整条连接共用一个 `Inflater`，每个矩形只是 zlib 流上的一段，而 `setInput` 会丢弃未消费输入，所以要逐字节对账（`drainInflaterInput`）。
- 只声明解得了的编码：写多一个 Tight，服务端立刻就用，解不了就是整屏花掉。
- 每矩形解完要求输入刚好用完，否则判「ZRLE 不同步」直接抛，宁可断也不显示错画面。

**可量化对照**：Raw 与 ZRLE 在同一场景（滚动、拖窗口）下的每帧字节数、解码耗时、CPU；ZRLE 单瓦片吞吐；大帧 P99；`Inflater` 复用与每矩形新建的正确性对照（后者必然出垃圾，是现成的反例实验）。

**最大软肋：真机零验证。** 仓库文档明写「真机零验证」，待验项第一条就是 ZRLE 的三处高危点，日志里只有「装进手机 + 待验证清单」，没有任何一条「画面出来了」的记录。**这条不解决就不能报。**

#### 候选二：OCI 镜像拉取与解包

只读实现 Registry HTTP API v2，把 `repo:tag` 流式变成可 `proot -r` 的 rootfs。1361 行，不引任何 registry 或容器库。

有真东西：401 换 Bearer token 的流程、manifest index 按 `arm64` 挑、`MAX_MANIFEST_HOPS=3` 防服务端决定递归深度把栈打爆、边下边解同时算 sha256、**OCI whiteout 语义**（`.wh.` 删下层、`.wh..wh..opq` 整目录作废，不处理就会残留已删文件）、手写 tar reader（ustar prefix、GNU 长名、硬链接）、路径逃逸校验，以及一条很漂亮的 Android 坑：`canonicalFile != absoluteFile` 在 Android 上恒为 true，导致整树 chmod 第一行就 return。

**弱点**：容易被评审归为「docker pull 的复刻」，创新性弱于候选一；`zstd` 层直接拒绝、`foreign` 层跳过，覆盖率有限。

#### 候选三：UI 观察契约中间件

核心主张很好听——「让看到的屏幕和动手时的屏幕可验证地是同一块，对不上就拒绝执行而不是点错」。有 `observation_id`、超时、前台包名、坐标命中元素四重校验，只存纯数据不持有无障碍节点句柄，还处理了平板上三套尺寸同时说话导致画面压扁 6% 的问题。

**但 `NodePostProcess.kt` 自述后处理链「借鉴 agent-mobile-use 的 ToolMain」**，四步顺序与思路是别人的。这一条必须标出来，否则就是硬伤。加上必须绑 Android 无障碍、无法纯 JVM 复现，排第三。

### 决策：mathengine 定为主报，不再摇摆

结论已定，理由只有一条：**mathengine 是这里唯一「已经证明自己是对的」的东西**。

- 4109 行 Rust，46 个单测全绿，纯算法不依赖设备。
- 有明确的替代对象（jlatexmath）与替换理由（GPL-2.0 传染、JVM 依赖、体积）。
- 结论可以在任何一台电脑上复现，不需要真机、不需要联网、不需要额外装什么东西。

其它候选的处理：

| 候选 | 处理 | 原因 |
|---|---|---|
| RFB(VNC) 客户端 | 不报 | 真机零验证，只有「待验证清单」 |
| OCI 镜像拉取 | 不报 | 会被读成 docker pull 复刻，创新性弱 |
| UI 观察契约 | 不报 | 后处理链自述借鉴他人，原创性有硬伤 |
| 中文检索索引 | 不报 | 绑 Android SQLite，脱离设备讲不完整 |
| 多协议适配 | 不报 | 与 AI 强相关，正好是同质化重灾区 |

一句话：**这次只交 mathengine。** 剩下的都写进技术档案，留给明年或省赛，不要在同一份申报里分散注意力。

同质化这个判断是对的。科创赛里「AI 助手」「智能问答」「语音识别」这类作品数量极多，评审一天看十几份，名字里带 AI 的会先被归堆。你手上的东西里，唯一不会被归堆的就是那个公式排版引擎。

### 怎么把 Arix 拆得不留痕迹

直接交 mathengine 会有个硬问题：它本来是 Arix 的一个模块，评审会问「这不就是你那个 AI 助手的一部分」。所以拆法不是删掉 Arix，而是**把 Arix 从作品降成背景故事**。

叙述顺序这样排：

1. **问题**：我在做一款跑在智能手表上的 AI 助手，需要显示数学公式。手表屏幕小、算力弱、没有 JVM 环境。
2. **现有方案的死路**：jlatexmath 是 GPL-2.0，接进应用有许可传染风险；它依赖 JVM，手表端跑不起来；体积也对小设备不友好。换别的库同样绕不开这几条。
3. **所以我写了一个**：纯 Rust、无 JVM 依赖、只做 TeX 数学模式的排版引擎，从 tokenizer 到 Box 布局全部自己实现，字体用 Latin Modern Math，通过 JNI 给 Android 用。
4. **验证**：四组对照实验的数据。
5. **落地**：已实际集成在手表端产品里使用。**这一条一句话带过，不要展开 Arix 的功能。**

关键点：作品主体始终是「排版引擎」，Arix 只是它被造出来的理由和使用现场。这样既不否认来源，也不会被拖进 AI 助手的同质化池子里。

**作品命名**：不要叫「Arix 数学渲染模块」。叫「面向移动端的轻量级 LaTeX 数学排版引擎」之类的，名字里不出现 Arix。

**关键词**填：数学排版；TeX；Rust；移动端；许可合规。不要填「人工智能」，一个字都别沾。

### 材料的三条改写原则

1. **数字降权，结论提权**。「859 次提交、11 个版本、430 个源文件」这类是苦劳，不是成果。评审看的是「你解决了什么问题、证据是什么」。这些数字放到附录，正文前两段留给问题与结论。
2. **动机提权**。mathengine 材料的第一段就该是「为什么不能用现成的」：jlatexmath 是 GPL-2.0，接进 Android 应用有许可传染风险；它依赖 JVM，手表上跑不动；体积也大。这三条是真理由，比「我喜欢造轮子」有力得多。
3. **边界诚实**。不支持的命令、没做的优化、已知的缺陷，主动列一节。这一节通常是评审加分的地方——它证明你知道自己的东西在哪不行。

### 答辩最可能被问的三个问题

| 问题 | 怎么答 |
|---|---|
| 「这跟现成的库比，好在哪？」 | 直接给数字：命令覆盖多少、耗时差多少、体积差多少。别说「更优雅」「性能更好」这类形容词 |
| 「哪些是你自己写的？」 | 明说第三方依赖（`ttf-parser`、`image`、`jni` 是库），自己写的是 tokenizer、AST、TeX Box 布局、FFI。**不要含糊，含糊等于承认有水分** |
| 「你那个 AI 助手呢？听说还有语音唤醒？」 | 一句话带过，不展开。唤醒不进任何材料，被问到就说「那是早期探索，没有达到可验证的程度，所以这次没报」 |

最后一条尤其重要：主动承认某部分没做好，比被评审翻源码翻出来强一百倍。

### 一个容易被忽略的点

评审真的会看源码。所以拆仓库的时候顺手做三件事：README 写清楚架构与构建方式、关键模块有注释、测试能一条命令跑起来。这三件事花不了两天，但它决定了评审对你「是不是真的自己做的」的第一印象。

### 第四轮：复用、稳定性与同类对比（提交 `e742d82`）

**代码复用**：`\binom`、`\left…\right`、矩阵环境三处各抄了一遍「把分隔符缩放到包住内容并垂直居中」的公式。抽成 `fit_delimiter` 与 `wrap_delimiters` 两个函数，三处共用。这类重复最危险的地方不是难看看，而是改一处忘另一处，导致一个包得住、一个包不住。

**稳定性**：新增 `tests/robustness.rs`，用固定种子的 LCG 从 38 个 token 随机拼出 2000 条输入（含孤立 `^`、未闭合 `\left(`、自造命令、中文），要求 0 panic、0 非法布局、0 非有限数值。

| 引擎 | 成功 | 拒绝 | 崩溃 |
|---|---|---|---|
| 本引擎 | 442 | 1558 | **0** |
| jlatexmath 1.0.7 | 420 | 1580（ParseException） | 0 |

拒绝率几乎相同（约 78%），口径可比。差别在拒绝方式：本引擎返回 `Err`，jlatexmath 抛异常。

**fuzz 抓到的真 bug**：单个 `-` 或 `=` 会算出负的 depth。原因是减号、等号的墨迹整个在基线上方，取反后得到负数，一路传成负尺寸。已修，这类输入人工测根本想不到。

**功能覆盖对比**（同一套用例，三个引擎读同一个文件）：

| 用例集 | 本引擎 | jlatexmath | KaTeX |
|---|---|---|---|
| 基础 30 条常用结构 | 30/30 | 30/30 | 30/30 |
| 进阶 20 条高级命令 | 19/20「不报错」，但大多按字面渲染 | 15/20 | 17/20 |

**这张进阶表不能只看数字。** 本引擎的宽容策略是未知命令按字面画出来，所以"成功"只表示没报错，不表示渲染正确。真实命令覆盖约 40 个，远窄于 KaTeX 与 jlatexmath 的数百个。这是必须承认的短板。

**改进方向（已写进文档）**：给 `Layout` 加 `unsupported: Vec<String>`，把被当字面渲染的命令报给宿主，让宽容从「悄悄画错」变成「画得出但告诉你哪不对」。

**效率**：重构后复测中位 3.20 µs、p95 8.58 µs，与上轮持平。体积 785 KB。

| 手段 | 效果 | 代价 |
|---|---|---|
| 字体子集化（4802 → 1853 字形） | 720 → 257 KB | 无，测试全过 |
